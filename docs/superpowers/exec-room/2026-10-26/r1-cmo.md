# CMO position paper, round 1: how the lean-sdd README looks and reads

No `.agents/product-marketing.md` exists in the repo (checked); the brief's target reader stands in for it. Sources: SKILL.md (S), CHANGELOG.md (C), GUIDE.md (G), archify SKILL.md (A), all under `~/.claude/skills/`.

## Position
- The README is a short argument for a skeptic: it is small, it fits next to superpowers, its rules are earned, and install is one command. Look: quiet, mostly text, four diagrams, no badge wall, no emoji.
- The hook is "two gates" (S:20: spec approval and merge are the only fixed gates), not "SDD". The reader wants fewer gates; lead with the number.
- The headline claim "every rule has a real failure behind it" is partly false today (see Risks). Ship it as "every rule cites its failure, or says it has none yet."
- Do not claim lower token cost vs superpowers. No such measurement exists in the sources. Measure it, or show only the numbers we do have.
## Reasoning
**Repo name.** Keep `lean-sdd` (S:2 skill name, G:1). It reads as a plugin name and is already the term in the CHANGELOG. GitHub description (one line): "Spec-to-merge workflow for Claude Code with two human gates. Replaces superpowers brainstorming, writing-plans and subagent-driven-development (S:8)."
**Tagline options** (pick one, put it as the H1 subtitle):
1. "Two gates. Evidence for everything else." (S:20-22). Recommended: short, a number, a promise the body can pay.
2. "The superpowers loop, minus the ceremony." Names the reader's tool, but "minus" implies a size claim we cannot yet show.
3. "A workflow skill whose every rule cites the session that broke it." Strongest proof, but only after the Risks fix.
**Hero, one screen (about 25 lines rendered).** Order: H1 + tagline; one sentence of what it is; 3 bullets; diagram 1 (workflow T to 9, S:13-18); install block; link row.
- Sentence: "lean-sdd runs a multi-step build in Claude Code: spec, plan, parallel build, review panel, merge. You approve two things, the spec and the merge. Claude asks you everything else in one batched question round." (S:20-23, S:69-80)
- 3 bullets, each sourced: (a) small tasks skip it, 1-3 files, no spec, no subagents (S:31-33); (b) cheap by default: Sonnet/medium correctness review, Opus only on a trust boundary, design seat only at about 300 new non-test lines (S:144-147); (c) the plan holds interfaces and tests, not code (S:96-101).
- Badges: none. One plain text line under the tagline: `MIT · Claude Code plugin · uses superpowers TDD and debugging`. A skeptic reads shields as decoration; text carries the same facts. Cost to owner: update the version by hand, 1 line per release. A version badge is the only one I would allow later.
- Install block: one fenced copy-paste command plus the one-time setup. The exact plugin command is not in the sources; owner supplies it. G:9 lists setup (superpowers, agents, scripts, statusline); the plugin must hide all of it, or the README says what is left.
**Visual system (GitHub-rendered only).** Each point below is syntax I know from GitHub docs, not re-verified this session. T1 below tests it.
- Diagrams: `<picture>` with `<source media="(prefers-color-scheme: dark)">` plus `<img>` light, two SVG files per diagram, 8 files. Archify lists SVG export and dark/light themes (A:3) but does not say a single run emits one SVG per theme. T1: export both themes, render in a private repo in both GitHub modes. Fallback if it fails: PNG pairs (more bytes, no zoom).
- Alt text on every `<img>` states the diagram's point in one sentence. Each diagram gets a caption sentence, because SVG text is not searchable or readable by screen readers inside `<img>`.
- Diagram placement: workflow T to 9 in the hero; task lifecycle after "What happens to one task"; sequence and architecture map inside `<details>` titled "How the coordinator and agents talk" and "Where the files live". Hero stays one screen.
- Tables: one table for "What it replaces vs keeps" (S:8-11), one for gates ("You approve / Claude decides / Claude asks you"). No table over 4 columns.
- Alerts: at most 3 in the whole README. `> [!NOTE]` for "works alongside superpowers". `> [!IMPORTANT]` for "two gates need an explicit yes" (S:20). `> [!WARNING]` for the usage-guard hook pausing at 95% (S:43-44). More than 3 and they become wallpaper.
- `<details>` for: full ledger line formats, the 9-step list, the CHANGELOG sample, setup troubleshooting. The summary text is the claim, not "Click to expand".
- Emoji: none. Skeptic reader, and a workflow README is read as a spec. Spacing: one H2 per beliefs step, a blank line around every block, no horizontal rules, line length under 100 chars so diffs stay clean.

One panel-security finding forged a ledger line, so `sdd-log.sh` refuses newlines (C:83).
- "We cut things" is the strongest line for this reader: Medium tier, Opus escalation, a 258-line GUIDE cut to 11 (C:71, C:74). Put these in a "Removed" list.
- Eval numbers (C:16: S1 12/9, S2 9/7, S3 12/11, new/old) have no stated unit or rubric in the sources. Cut them from the hero. Show only after the owner states what the scores count.
- sdd-metrics: the script prints tasks, fix rounds, coord fixes, blocked, findings per seat, 5h usage (S:187-188, G:10). No real output line is in the sources. Owner picks one finished plan and pastes its true line as a sample block; mark it "one project, one maintainer."
- Token cost: n=1 only, about 9k tokens per implementer (C:81). Not a comparison. Do not publish as a saving.
**Origin and stack neutrality (owner constraint, added after the first draft; source: coordinator message, repo `github.com/alchristleo/agentic-warden`, a Go/auth project; I did not open it).**

For the README, restate them as "the command that checks it" with a placeholder (`<your test command>`); the skill text itself is the owner's call.

**Credits.** A "Built on" section near the end, one line each, with what was taken: superpowers (TDD, systematic debugging, finishing: S:8-11); archify (diagrams, MIT, tt-a1i, A:4-8); asd-ste100 (bundled lint, MIT, third party, brief); poteto skills (verify-this, prove-it-works, reflect, interrogate: C:8-11); Pocock (retro, diagnosing-bugs: C:11, C:17). Link each repo. The links and license texts come from the owner; I did not check the repos. Credit early readers' trust: this section is also a signal to the superpowers audience.
**Launch channels (sequenced).** 1) A GitHub topics + description pass at publish (`claude-code`, `claude-code-plugin`, `agent-skills`). 2) A post to the superpowers community or issues as "here is a lean variant", respectful, not a replacement pitch. 3) One long post (the "why two gates" story with the C evidence) on the owner's own blog or a Show HN style page. 4) Claude Code Discord/subreddit threads where users complain about cost. I have no data on which channel converts; start with 1 and 2 (cost: about 1 hour each, no maintenance).
**Reference bar (from memory, not reopened this session; owner opens each before copying anything).** 1) `BurntSushi/ripgrep`: opens with a plain claim, then a benchmark table with method and where rivals win; the honesty is the proof. 2) `charmbracelet/vhs` or `glow`: one short pitch, one visual, install near the top; shows how little text a hero needs. 3) `obra/superpowers`: the neighbor the reader already knows; match its install clarity, do not copy its tone.
## Risks
- C:49 and C:37 and C:5-6 admit entries with no session failure ("no session failure yet", "not rerun as eval", user-rule entries). The headline "every rule has a real failure" would be disproved by a reader opening the CHANGELOG. This is the biggest credibility risk.
- The CHANGELOG spans 2026-10-23 to 2026-10-26 (C:5-88): four days, one maintainer. Say so in the README; the reader will check.
- C names project milestones ("hosted cells", "platform refresh", "agent-wrapper") and `~/.claude` paths. Per the owner they may stay as a case study, but a reader needs one line saying these are milestones of the linked repo, and `~/.claude` paths must match the plugin layout. Cost: one pass over 82 lines, plus an "is each linked artifact public" check.
- Origin in a Go/auth repo can read as "only for Go services". Keep the origin out of the hero and the rules stack-neutral (see Origin section).
- GitHub rendering of dual-theme SVG is unverified (see T1). If it fails, the four diagrams ship as PNG.
- A README that promises "lean" while the skill is 222 lines and about 80 CHANGELOG entries invites the sneer. Show the numbers: "one 222-line skill file" is a fact (S).
## Options for the owner
1. **Recommended: "Two gates" evidence README.** H1 + tagline 1, text-only hero line, diagram 1, install, 3 sourced bullets, gates table, 3 alerts max, 3 `<details>`, a "Removed" list, 4 sourced failure lines, a real sdd-metrics sample, credits, honest scope note ("4 days, one maintainer"). Headline softened to "every rule cites its failure or says it has none". Cost: README about 150-180 lines; 8 SVG files to regenerate on diagram change; one CHANGELOG pass (milestone names, links, paths); one stack-term grep; one T1 render test (about 30 min); one real metrics sample from a finished plan.
2. **Minimal README.** Tagline, pitch, install, diagram 1, link to CHANGELOG as the proof. The other 3 diagrams live in `docs/`. Cost: lowest to maintain, but it breaks the fixed decision (README has 4 diagrams) unless the owner relaxes it, and it hides the proof.
3. **Comparison-led README.** Add a "lean-sdd vs superpowers" table with token and gate counts. Strongest hook for this reader. Cost: needs a measured A/B on one task (same prompt, token counts, both workflows), a re-measure per release, and it invites dispute. Do this only after the owner has the measurement; otherwise cut.
